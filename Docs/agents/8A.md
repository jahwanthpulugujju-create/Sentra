## 3. Task list

### 8A-a — Concept & framing (REQUIRED, no code) — `BUILD_PLAN §8A.1–8A.4, 8A.8`
Confirm you can state each of these (they're the judge-facing story):
- [ ] ✅ Mental model: the platform is a **tool, not a rail** — it sits between the
      agent's intent to pay and money moving; the agent can only ask, and this is the
      only thing that can say yes. (§8A.1)
- [ ] ✅ Two AI locations kept distinct: (A) the external **agent** that spends
      (simulated by a button in the MVP) vs. (B) the internal **intent-match** call.
      (§8A.2)
- [ ] ✅ The **5-step pattern**: tool def → agent emits `request_payment` → **app code
      intercepts & forwards to `POST /evaluate-transaction`** → Allow/Escalate/Deny →
      app acts (spend / block for human / fail). The load-bearing step is #3. (§8A.3)
- [ ] ✅ What's **real vs simulated** in the demo: the button *is* the agent's tool
      call; steps 3–5 are exactly production. (§8A.4)
- [ ] Memorize the one-liner (§8A.8): *"Any agent framework gives its agent a
      `request_payment` tool. That tool doesn't spend — it calls us. Only an Allow ever
      reaches the real rail. The agent can ask, but we're the only thing that can say yes."*

### 8A-b — Security boundary (REQUIRED) — `BUILD_PLAN §14, §8A.5`
- [ ] ✅ Audit the codebase: the `agent_id` an evaluation spends against is **injected
      by the app/harness, never supplied by an agent's model output.** An agent must
      not choose which identity (and budget) it spends as — that's an authorization
      boundary.
- [ ] ✅ Confirm the tool contract (§8A.5) maps `amount→amount`, `reason→description`,
      and that **`agent_id` is NOT a tool parameter** — in any agent code it is a code
      constant. (This mirrors the §9 security-review item.)

### 8A-c — Real Claude agent loop (STRETCH — only if M0–M5 solid + user opts in)
Standalone; never a dependency of the core demo. `BUILD_PLAN §8A.5–8A.6`; `claude-api` skill.
- [ ] Create a separate `agent_demo/` folder (isolated from `backend/`, `frontend/`).
- [ ] `agent_demo/requirements.txt`: `anthropic`, `requests`.
- [ ] Implement `agent_demo/run_agent.py` per `BUILD_PLAN §8A.6`:
      - Define the `request_payment` tool exactly per §8A.5 (`vendor`, `amount`,
        `reason` — **no `agent_id`**).
      - Run a Claude tool-use loop (agent model per §1; loop while `stop_reason ==
        "tool_use"`; append full `resp.content`; return all `tool_result` blocks in one
        user message) — call shape from the `claude-api` skill, not from memory.
      - On a `request_payment` call, **the harness code** (not the model) POSTs to
        `http://localhost:8000/evaluate-transaction` with a **hardcoded `AGENT_ID`** +
        the model's `amount`/`reason`, and returns the verdict string as the tool result.
- [ ] (Optional deeper) On **Escalate**, poll `GET /transactions` until the `pending`
      row is resolved by a human, then feed the final verdict back to the agent.
