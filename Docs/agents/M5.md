## 0. Operating rules (non-negotiable — same as M0–M4)

1. **No hallucination.** Do not invent test expectations, seed numbers, README
   commands, or behavior. Every artifact traces to a `BUILD_PLAN.md` section
   (§6.1 rules, §9 UI, §11 setup, §13 tests, §5 canonical data, §14 security). If
   a detail is not documented, do **not** guess — see rule 3.
2. **Read the docs first, act second.**
3. **If something is unknown or unresolved, STOP and ASK the user.** Known gates
   are the Precondition and §1; for any other ambiguity, ask rather than assume.
4. **Harden, don't rewrite.** M5 is about robustness and polish. Do **NOT** add new
   product features, change the decision logic, or alter the canonical numbers.
   If you find a real bug, fix it minimally and note it.
5. **Stay in scope.** M5 builds ONLY: UI error-state hardening, edge-case
   verification, a styling pass, `backend/test_smoke.py`, a root `README.md`, and a
   consistency audit — then the 5× rehearsal. Do **NOT** build any `§15` stretch.
6. **Security review before any commit/push.** This project touches
   payments/DB/secrets/inputs — before the user pushes, run the review in
   `BUILD_PLAN §14` (see also `TODO §9`). Do not commit/push unless asked.
7. **Verify, don't assume.** A check passes only when observed directly (a real
   passing `pytest` run, the real demo running 5× clean), not because it "should."

## 3. Task list — M5 (mirrors `TODO.md §7`)

Read the cited section before each item.

### 3.1 Verify the rule engine is real (`BUILD_PLAN §6.1`)
- [ ] Confirm blocklist + velocity are fully implemented (not stubs) and behave per
      §6.1 — covered by the M1 acceptance (blocklist-deny, velocity-deny). If the
      smoke test (3.5) doesn't already cover them, add cases.

### 3.2 Graceful UI error states (`BUILD_PLAN §9`)
- [ ] Confirm the UI never blanks/crashes on failure and shows a readable message
      for: backend down (offline banner), a failed evaluate (ProcessingPanel error),
      a failed resolve (EscalationCard error). Fill any gap you find. No raw stack
      traces or silent failures in front of a judge.

### 3.3 Edge cases (`BUILD_PLAN §6.3`)
- [ ] Confirm no divide-by-zero / crash for: an agent with `< 2` history (not
      flagged), `std == 0` history, a zero/negative amount (rejected 422), an unknown
      agent (404), and a malformed transaction id on resolve (404). Add a guard only
      where one is genuinely missing.

### 3.4 Styling pass (`BUILD_PLAN §9`; palette per §1)
- [ ] Polish to match the pitch deck: navy structure, amber for decisions/emphasis,
      semantic green/red; legible on a projector (contrast, sizes, budget bars,
      chips, banners). Keep colors sourced from `theme.js`. Do not restructure
      components — visual polish only.

### 3.5 Smoke test (`BUILD_PLAN §13`, §5)
- [ ] Add `pytest` (dev dependency).
- [ ] Write `backend/test_smoke.py` that, against a freshly-seeded DB, locks the
      **four canonical scenarios' decisions** (`BUILD_PLAN §5`): scenario 1 → Allow,
      scenario 2 → Escalate, scenario 3 → Escalate, scenario 4 → Deny (budget). Drive
      the policy engine (or the API) directly; reset/reseed at the start.
      **Note:** with no Claude key, intent runs the fallback — scenario 2 still
      Escalates but via intent, not anomaly (assert on the **decision**, not the
      trigger, unless a key is guaranteed). Ref: `Docs/agents/M3.md` §5 nuance.
- [ ] ✅ Run `pytest` — the four scenarios pass.

### 3.6 README (`BUILD_PLAN §11`)
- [ ] Write a repo-root `README.md` quickstart derived from §11: prerequisites,
      one-time setup (Supabase schema, `.env`), and the run commands for backend +

### 3.7 Consistency audit (`BUILD_PLAN §5`)
- [ ] ✅ Verify every number shown in the UI matches `BUILD_PLAN §5` (budgets,
      balances, preset amounts) **and** the pitch deck. Fix any drift.

## 5. When to STOP and ask the user (explicit gates)

Stop and ask — never guess — if:
- M0–M4 aren't all green/observed-live (Precondition) — can't harden an unfinished app.
- The palette, project name, or the test-DB approach (§1) is unresolved.
- A test expectation, README command, or number isn't derivable from `BUILD_PLAN.md`
  (§5/§11/§13) — ask rather than invent it.
- Hardening would require changing decision logic or canonical numbers — that's out
  of scope (rule 4); confirm with the user before any such change.
- The 5× run reveals a real bug that needs a non-trivial fix — report it and confirm
  the fix approach before large changes.

Report concisely:

2. **What was hardened vs. already-robust** — per 3.1–3.4, what you changed vs. only verified.
3. **Test result** — the actual `pytest` output for the four scenarios.
4. **Acceptance results** — README present? consistency clean? the 5× run outcome.
5. **Decisions used** — palette, project name, test-DB approach.
6. **Security review** — remind the user it must run before any push (`BUILD_PLAN §14`).
7. **Blockers/asks** — anything from §5.
8. **Next:** "M5 complete — core build demo-ready. Optional stretch = §15 on your go."

Do not report success for any check you did not actually observe — especially the
5× clean run, which is the whole point of M5.
