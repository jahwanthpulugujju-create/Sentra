# Agent Runbook — M6: Buffer & Rehearsal (Demo-Ready)

> **You are executing ONLY Milestone M6 — the final buffer.** This milestone is
> mostly **rehearsal and readiness**, not building. Do not add features or start
> stretch work (`BUILD_PLAN §15`). When M6's acceptance passes, the project is
> demo-ready. Then STOP.
>
> **Goal of M6:** make the demo bulletproof in front of judges — rehearse it 5×
> clean, memorize the pitch + the killer Q&A answers, fix the single most-fragile
> thing, and confirm the app degrades gracefully (fallback + amber badge) on bad
> wifi.
>
> Source of truth: `Docs/BUILD_PLAN.md` (esp. §16 runbook, §17 judging),
> `Docs/PROJECT_BRIEF.md` (positioning §1, business model §8), `Docs/TODO.md §8`.
> This file is the *how-to-run-M6*; the plan docs hold the *exact content*.

## 0. Operating rules (non-negotiable)

1. **No hallucination.** Do not invent pitch claims, market/revenue numbers, or
   Q&A answers. The pitch content lives in `PROJECT_BRIEF.md` (§1, §8) and
   `BUILD_PLAN.md` (§16, §17). Use those; if a fact isn't there, do **not** make one
   up — see rule 3.
2. **Read the docs first.** The demo runbook is `BUILD_PLAN §16`; follow it exactly.
3. **If something is unknown or unresolved, STOP and ASK the user** (venue/wifi,
   who presents, whether the deck is ready — see §1).
4. **M6 is rehearsal, not building.** The ONLY code change allowed is fixing the
   *single most-likely-to-break* thing found during rehearsal — and that fix must be
   minimal and doc-faithful. No refactors, no new features, no styling overhaul, no
   stretch. If rehearsal reveals a big problem, report it and ask before large changes.
5. **Do not commit or push** unless the user asks; if asked, run the security review
   (`BUILD_PLAN §14` / `TODO §9`) first.
6. **Verify by doing.** "Rehearsed" means the demo was actually run start-to-finish,
   not read about. Report only what was actually run/observed.

## 3. Task list — M6 (mirrors `TODO.md §8`)

### 3.1 Rehearse the demo end-to-end, timed (`BUILD_PLAN §16`)
- [ ] Run the full demo per the `BUILD_PLAN §16` runbook, start to finish, **timed**,
      at least **5 times**, with a **Reset between each**:
      set the scene → normal (scenario 1, Allow) → the hijack (scenario 3, Escalate)
      → **Deny live** → (optional) let someone type a custom request → close on the
      audit log. The "catch" must land cleanly every time.
- [ ] Confirm the timing fits the slot (§1). Trim narration if over.

### 3.2 Memorize the pitch + the killer Q&A (`PROJECT_BRIEF §1, §8`; `BUILD_PLAN §16, §17`)
- [ ] The opening **2 a.m. story** and the close (the "traffic cop" one-liner) —
      `BUILD_PLAN §16`.
- [ ] The **"how is this different from Visa/Stripe?"** answer, word-for-word:
      *"they're the rails; we're the judgment layer — none of them check whether a
      transaction is semantically consistent with what the agent is supposed to be
      doing."* (`PROJECT_BRIEF §1`, `BUILD_PLAN §16/§17`). It must come out instantly.
- [ ] The **market / revenue / use-case** points, in case a judge asks (`PROJECT_BRIEF
      §8`, `BUILD_PLAN §17`): who pays (fintechs, enterprises, agent-orchestration
      platforms); revenue (governance SaaS — per-agent/seat, screening fee as upsell);
      the use case (the audit-trail + kill-switch is the blocker before agents can hold
      a company card). Do **not** invent dollar figures not in the docs.
- [ ] Whole team can present **any** part (`BUILD_PLAN §17`).

### 3.3 Fix the single most-likely-to-break thing (minimal)
- [ ] From rehearsal, identify the one thing most likely to glitch live (a slow LLM
      call, a race, a confusing UI moment). Fix **only that**, minimally and
      doc-faithfully. Re-run the demo to confirm. If the fix is non-trivial, STOP and
      ask before changing much (rule 4).

### 3.4 Verify graceful degradation on bad wifi (`BUILD_PLAN §16`)
- [ ] Simulate/observe the LLM path failing (e.g. no key, or offline): confirm the
      intent check falls back to the keyword heuristic, the health badge goes **amber**
      ("fallback"), and **nothing visibly breaks** — the demo still runs and the catch
      still fires (scenario 3 escalates under fallback too).
- [ ] Know the honest line if asked: on bad wifi the system uses the local fallback
      and says so via the amber badge.

### 3.5 Pre-demo checklist (run right before judges — `BUILD_PLAN §16`)
- [ ] Backend + frontend running; `/health` green; click **Reset** for a clean state;
      dashboard open and full-screen; the hijack preset ready.

## 5. When to STOP and ask the user (explicit gates)

Stop and ask — never guess — if:
- M0–M5 aren't confirmed complete/live (Precondition) — nothing to rehearse.
- A pitch fact, market/revenue point, or Q&A answer isn't in `PROJECT_BRIEF.md` /
  `BUILD_PLAN.md` — ask; do not invent claims or numbers.
- Rehearsal reveals a bug whose fix is non-trivial or would change scope/logic
  (rule 4) — report it and confirm the approach before large changes.
- Venue/wifi/deck/presenter details (§1) are unresolved.

## 6. Report format (when M6 is complete or blocked)

Report concisely:
1. **Rehearsal outcome** — how many clean runs, timing vs. slot, any glitch found.
2. **The one fix** — what was most-fragile, what you changed (minimal), re-tested?
3. **Graceful degradation** — fallback + amber badge confirmed?
4. **Pitch readiness** — story + Visa/Stripe answer + market/revenue rehearsed?
5. **Blockers/asks** — anything from §5.
6. **Next:** "M6 complete — demo-ready. Optional: stretch (`§15`) / security review
   before any push (`§14`)."

Do not report the demo as rehearsed unless it was actually run start-to-finish.
This is the last line of defense before judges — "it works on my machine" is not
"it ran 5× clean." Only the latter counts.
