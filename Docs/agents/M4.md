## 2. Prerequisites & scope

### 2.1 Already in place (do not rebuild)
- [ ] `evaluate` already writes `status:"pending"` with **no deduction** on Escalate
      (done in M3). **Verify this is true**; do not change it. If it deducts on
      escalate, that's an M3 bug — fix there, not here.
- [ ] `resolve(body)` fetch wrapper already exists in `frontend/src/api.js` (defined
      in M2). Use it; do not add a duplicate.

### 2.2 SECURITY — the one thing M4 must get right (BUILD_PLAN §14)
Approving/denying is a money operation. The endpoint MUST:
- [ ] **Guard on state:** only act if the transaction's current `status == "pending"`.
      If it is anything else (already `approved`/`denied`), return **409** and do
      nothing. This prevents an escalation being approved twice (double-spend).
- [ ] **Be atomic:** perform the balance update **and** the status flip **and** the
      `resolved_at` set in a **single DB transaction**, so a partial failure can't
      leave money moved without the status recorded (or vice-versa).
- [ ] **Deduct only on approve:** `approve` → subtract `amount` from the agent's
      balance, `status="approved"`. `deny` → **no** balance change, `status="denied"`.
      Both set `resolved_at`.
- [ ] Validate `transaction_id` (unknown → **404**) and `action` (must be
      `approve`/`deny` → 422 via `ResolveRequest`).
