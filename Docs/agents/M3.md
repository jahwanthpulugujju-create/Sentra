## 0. Operating rules (non-negotiable — same as M0–M2)

1. **No hallucination.** Do not invent the intent prompt, the model id, SDK call
   shape, the anomaly formula, thresholds, `checks` fields, or reason strings.
   Every artifact traces to a `BUILD_PLAN.md` section (§6.2 intent, §6.3 anomaly,
   §6.4 combine, §9 UI) or the `claude-api` skill. If a detail is not documented,
   do **not** guess — see rule 3.
2. **Read the docs first, act second.** Read the cited section (and, for the
   Anthropic call, the `claude-api` skill) before writing code.
3. **If something is unknown or unresolved, STOP and ASK the user.** Known gates
   are the Precondition and §1; for any other ambiguity, ask rather than assume.
4. **The decision is made in code, not by the model.** The Claude call returns
   only a JSON verdict `{match, reason}`; the Allow/Escalate/Deny decision is
   computed by `policy_engine` per §6.4. Never let the model's text drive control
   flow or be executed. (Prompt-injection safety — `BUILD_PLAN §14`.)
5. **Stay in scope.** M3 builds ONLY: `intent.py`, `anomaly.py`, the updated
   `policy_engine.evaluate` (now producing Escalate), and the frontend
   `ProcessingPanel` (3 chips + `DecisionBanner`). Do **NOT** build the
   `EscalationCard` Approve/Deny flow or the `POST /resolve-escalation` route —
   that is **M4**. (See §2.2.)
6. **Do not commit or push** unless the user explicitly asks; run the security
   review (`BUILD_PLAN §14`) first if asked (LLM I/O + payments touched).
7. **Verify, don't assume.** An acceptance check passes only when observed
   directly (a real decision from the running backend / the real UI), not because
   the code "should" work.

## 2. Prerequisites & scope

- [ ] `anthropic` is already in `backend/requirements.txt` and installed (M0). Do
      not add new deps. Construct the client per the `claude-api` skill (the key is

### 2.2 SCOPE BOUNDARY — read before building (prevents M4 creep)
- M3 makes **Escalate** a possible decision. On Escalate, `policy_engine` writes
  the row with `status = "pending"` and **no balance deduction** (per §6.4). That
  is the full extent of escalation in M3.
- Do **NOT** build in M3: the `EscalationCard` with Approve/Deny buttons, or the
  `POST /resolve-escalation` route/logic — those are **M4**. In M3 a `pending` row
  simply sits in the ledger (visible in the audit log) with no way to resolve it
  yet; that is expected.

### 2.3 Expected behavior change (not a regression)
- In M1/M2 (rules-only), scenarios 2 and 3 resolved to **Allow**. After M3 they
  become **Escalate** (that is the whole point). Do not treat this as a bug.

## 3. Task list — M3 (do in order; mirrors `TODO.md §5`)

Read the cited section before each file. Do not restate specs from memory.

### 3.1 Intent match (`BUILD_PLAN §6.2`; `claude-api` skill)
- [ ] Implement `backend/intent.py::check_intent(task, amount, description)`:
      - Make **one** call to Claude **`claude-haiku-4-5`** using the **exact prompt
        in §6.2**, via the Anthropic Python SDK (call shape per the `claude-api`
        skill — a plain classification call; **no** `thinking`/`effort` params).
      - Parse the reply as strict JSON `{match, reason}`; tag `source:"llm"`.
      - **Fallback (must not raise):** on missing key / API error / malformed JSON,
        use the keyword-overlap heuristic described in §6.2; tag `source:"fallback"`.
      - Return `{ran: true, match: bool, source: "llm"|"fallback", reason: str}`.
- [ ] ✅ Confirm the model id `claude-haiku-4-5` matches the `claude-api` skill's
      current-models list (it does) — no date suffix.

### 3.2 Anomaly score (`BUILD_PLAN §6.3`)
- [ ] Implement `backend/anomaly.py::score_anomaly(agent, amount, db)` **exactly**
      per §6.3: pull this agent's prior `allowed`/`approved` amounts; if `< 2` →
      `{ran: true, flagged: false, ...}` ("not enough history"); else compute
      `mean`, `std` (guard `std == 0`), `z = (amount - mean) / std`, flag if `z > 2`.
      Return `{ran, flagged, z_score, mean, std, reason}` with the §6.3 reason string.

### 3.3 Wire into the policy engine (`BUILD_PLAN §6.4`, §4)
- [ ] Update `backend/policy_engine.evaluate` so that when the rule engine passes,
      it runs **intent match** and **anomaly**, records their real results in the
      `checks` blob (replacing the M1 `ran:false` stubs), sets `intent_source`, and
      combines per §6.4:
      - rules fail → **Deny** (unchanged);
      - rules pass + intent `match` true + anomaly not flagged → **Allow** (deduct);
      - rules pass + (intent `match` false **or** anomaly flagged) → **Escalate**,
        `status="pending"`, no deduction, with `triggered_by`/`reason` from **intent
        first, then anomaly** (per §6.4).

### 3.4 Frontend processing panel (`BUILD_PLAN §9`)
- [ ] Implement `ProcessingPanel.jsx`: on submit, animate the three check chips in
      sequence (Rule engine → Intent match → Anomaly, ~300ms each), then reveal the
      `DecisionBanner` (green Allow / amber Escalate / red Deny) from the response,
      with expandable detail showing the anomaly `z_score`, the intent `reason`, and
      the `source` tag. Drive the chip pass/fail states from the returned `checks`
      blob. Integrate it where the request result is shown (replacing the M2
      one-line result). Do NOT add Approve/Deny controls (M4).
